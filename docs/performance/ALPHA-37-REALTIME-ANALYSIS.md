## 修复生效，但工作量减少不足

四段 CACHE 候选合计 3,190,714 次查询、6,299 次命中，命中率约 0.197%；每段训练写入 6,200–6,375 次。入口不再为零，alpha.37 的默认法线准入修复已得到实机覆盖。约 99% 的查询依然回退完整路径。

四段 SPARSE 候选共复用 47,651 / 3,800,640 条主路径，约 1.25%。组合候选复用 163,630 / 3,800,640，约 4.31%，完整路径密度仍约 0.957；缓存合计命中 16,388 / 2,984,578，约 0.55%。与目标 0.25–0.6 的完整路径密度仍有很大距离。

组合组各段中位数的算术平均：primary 1.1803→1.4926ms（增加约 0.312ms），resolve 0.0201→0.0537ms（增加约 0.034ms）；bounce1 2.3632→2.3172ms，bounce2 2.0157→1.8904ms，两者减少约 0.171ms。这些分阶段描述不是独立稳定性证明，也不能将各 scope 的中位数相加当成整帧时间；它们说明当前省下的工作不足以抵消入口与历史开销。

## 新定位：缓存失效过频与成熟策略矛盾

CACHE 各段 start/end 的 radianceCacheEpoch 分别 5→9、10→14、5→8、11→13；组合各段 7→14、15→18、6→11、12→15。单段 10 秒采样中多次全局失效，而世界 cell 至少 24 次观察才允许查询。

第一段 CACHE 的 sun direction 从 (-0.44056,0.89772,0) 到 (-0.48705,0.87338,0)，lightAngle 从 26.15° 到 29.15°；手持灯位置与启用状态不变。生产 RtLightingChange 从 anchor 的方向差平方 >0.0004（约 1.15°）就触发全局 runtimeEpoch 更新；普通世界时间推进足以跨过此阈值。该阈值与频繁 epoch 更新有直接对应的代码依据，但现有导出没有逐次失效原因，不能把所有 epoch 更新全部归因于日光。

此外，cache 准入用单次训练样本的相对方差，而非缓存均值的估计误差；高蒙特卡洛噪声的间接光即使训练累计更多样本，也可能长期不满足该门槛。近处 TTL 为 16 帧，冷 cell 更新概率又随 capacity/budget 缩小，分散训练会使成熟困难。这些机制均可从生产代码确认，但现有计数把 epoch/count/TTL/key/plane/variance 拒绝合并为 cache_rejected，尚不能定量分摊各项责任。

稀疏 high_variance 计数实际包含所有 interval==1 的表面，既包括方差大，也包括置信度不足；不能据此声称这几十万个样本全部是高方差。下一步需要拆分置信度与方差原因，而不是简单把方差阈值取消。

## 后续修复重点

1. 导出 cache 拒绝的 epoch、成熟计数、TTL、空间与方差原因，以及全局失效来源；区分 sparse 方差与更新次数不足。
2. 分离渐变光照更新、硬编辑失效和屏幕历史置信度；普通日夜推进采用有界刷新，避免每次方向阈值都使整个世界缓存重新冷启动。保持突变/编辑正确性。
3. 训练预算优先覆盖实际查询的未成熟 cells，使用适合均值精度的误差指标，同时保留空间/漏光保护。需要检测过期样本与光照漂移，不能只除以样本数制造命中。
4. 在减少路径之前控制 primary/历史读取成本；rough diffuse 含未着色镜面分量，继续避免整体 RGB 按反照率缩放。调整调度必须同时验收参考画质。

当前没有必要重跑同一 alpha.37 测试；数据已足够说明瓶颈。下一版需要算法更新与更细的拒绝统计，再进行 GPU 与 reference 画质复测，不能宣布第三轮完成或执行层冻结。
